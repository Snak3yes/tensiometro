## 📋 Overview

This directory contains the **Claude Code implementation** of the Conductor system, inspired by the [Gemini CLI Conductor extension](https://github.com/gemini-cli-extensions/conductor).

The Conductor system enables **context-driven development** by managing project context as version-controlled artifacts, ensuring a persistent "source of truth" for all development work.

## 🚀 Usage

### Initial Setup

To run the Conductor setup for your project:

```bash
# Option 1: Interactive (via Claude Code)
# Use AskUserQuestion tool to conduct interviews

# Option 2: Automated (with pre-collected responses)
python claude-conductor/run_setup_with_responses.py
```

### What Setup Does

The setup process:
1. **Checks** if setup was already completed
2. **Conducts** 4 structured interviews:
   - Product Vision & Context
   - Product Guidelines & Standards
   - Technology Stack
   - Workflow & Development Preferences
3. **Generates** documentation in `conductor/`:
   - `product.md`
   - `product-guidelines.md`
   - `tech-stack.md`
   - `workflow.md`
   - `tracks.md`
4. **Saves** state to `conductor/setup_state.json`

### Generated Documentation Location

**IMPORTANT:** Generated documentation goes to the **original `conductor/` directory** (Gemini reference structure), NOT `claude-conductor/`.

```
conductor/                    # Original Gemini structure (GENERATED DOCS GO HERE)
```

### Interview Templates

Located in `interview_templates/`, these JSON files define structured questions:

- **product_vision.json** - Product type, users, goals, features
- **product_guidelines.json** - UI/UX style, theme, tone, error handling
- **tech_stack.json** - Languages, frameworks, database, testing
- **workflow_preferences.json** - TDD, coverage, commits, checkpoints

**Format:**
```json
{
  "phase": "phase_name",
  "title": "Display Title",
  "description": "Phase description",
  "questions": [
    {
      "id": "question_id",
      "type": "single_choice|multi_choice|text",
      "header": "Short Label",
      "question": "Full question text?",
      "options": [
        {"label": "Option", "description": "What it means"}
      ]
    }
  ]
}
```

### Document Templates

Located in `templates/`, these Markdown files use placeholders:

**Example:**
```markdown
# Product Guide

## Product Vision
{product_description}

## User Personas
{user_personas}

---
*Generated by Conductor. Last updated: {timestamp}*
```

**Placeholders** are replaced by `SetupAgent` during generation.

## 🔧 SetupAgent API

### Class: `SetupAgent`

**Location:** `setup_agent.py`

```python
from setup_agent import SetupAgent

# Initialize
agent = SetupAgent(project_root="/path/to/project")

# Run setup (automated mode)
responses = {
    "product_vision": {...},
    "product_guidelines": {...},
    "tech_stack": {...},
    "workflow_preferences": {...}
}
result = agent.run_setup(responses_dict=responses)

# Run setup (interactive mode)
result = agent.run_setup()  # Returns interview phases
```

### Key Methods

```python
# Check if setup exists
agent.check_existing_setup() -> bool

# Load interview template
agent.load_interview_template(phase: str) -> dict

# Generate documentation
agent.generate_product_md() -> str
agent.generate_workflow_md() -> str

# Persist state
agent.save_state(step: str)
agent.write_documentation()
```

## 🎯 Workflow Integration

### TDD Protocol (from workflow.md)

The generated `workflow.md` defines strict TDD workflow:

1. **Select Task** from `plan.md`
2. **Mark In Progress** `[~]`
3. **RED Phase:** Write failing tests
4. **GREEN Phase:** Implement to pass tests + smoke test
5. **REFACTOR Phase:** Improve code while tests pass
6. **Verify Coverage** (target from setup)
7. **Commit with conventional message**
8. **Attach git note** with detailed summary
9. **Update plan.md** with commit SHA `[x] abc1234`
10. **Commit plan update**

### Phase Checkpoints

At end of each phase:
1. Identify changed files (`git diff`)
2. Verify test coverage for all files
3. Run full test suite
4. Generate manual verification plan
5. Wait for user approval
6. Create checkpoint commit
7. Attach verification report (git note)
8. Update plan.md with checkpoint SHA

## 🆚 Comparison with Gemini CLI Conductor

| Feature | Gemini CLI | Claude Conductor |
|---------|-----------|------------------|
| Setup Flow | ✅ `/conductor:setup` | ✅ Implemented |
| Interactive Interviews | ✅ Yes | ✅ Yes (AskUserQuestion) |
| Document Generation | ✅ Basic | ✅ Template-based |
| State Persistence | ✅ Yes | ✅ Yes + responses JSON |
| Track Creation | ✅ `/conductor:newTrack` | 🚧 In Progress |
| Implementation | ✅ `/conductor:implement` | 🚧 In Progress |
| Test Coverage | ⚠️ Optional | ✅ **Mandatory (>80%)** |
| Git Notes | ⚠️ Basic | ✅ **Detailed summaries** |
| Smoke Tests | ❌ Not mentioned | ✅ **After each task** |
| Checkpoints | ✅ Yes | ✅ **Optional per track** |
| Auto-detection | ⚠️ Limited | ✅ **Tech stack from codebase** |

### Our Advantages ✨

1. **Mandatory Test Coverage** - Enforces >80% coverage (configurable)
2. **Detailed Git Notes** - Every commit has comprehensive summary
3. **Automatic Smoke Tests** - Application tested after each task
4. **Tech Stack Auto-Detection** - Analyzes codebase to detect frameworks
5. **Flexible Checkpoints** - User decides per track (not forced)
6. **Template System** - Conditional document generation based on preferences
